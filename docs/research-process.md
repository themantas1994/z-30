# Research process: how a change reaches `main`

Every change to z-30, from a one-line receiver tweak to a protocol revision, follows the same
path. It exists because the project has retracted sensitivity claims before (`AGENTS.md` §5,
`audit/`), and each retraction traced back to a change that was measured once, by its author,
on conditions that favoured it.

```
proposal → experiment against main → review (code, DSP, QA reproduction) → board decision → merge
```

**Nothing merges to `main` without the board's explicit acceptance.** A green CI run, an
approving code review or a good benchmark is evidence for the board, not permission to merge.

> **All measurement in this process is software simulation** unless it names a recording in
> `hardware-validation/`. Hardware and on-air tests are run only by the licensed board operator;
> nobody else keys a radio, drives PTT or transmits as part of an experiment
> ([hardware-validation.md](hardware-validation.md), [safety.md](safety.md)).

---

## 1. Proposal

Open a GitHub issue (or the tracking task) before writing code that is meant to change a result.
It states:

| | |
| :--- | :--- |
| **Claim** | What is expected to change, in the benchmark's own terms: "50% AWGN crossing moves from −23.00 dB by ≥ 0.2 dB", not "better sensitivity" |
| **Class** | Receiver-only, engine/station, tooling/docs, or **protocol** (section 6) |
| **Benchmarks** | Which `z30 --benchmark` runs decide it, at which points, how many frames per point |
| **Decision rule** | Written down **before** the run: the effect size and confidence that would accept it, and what would reject it |
| **Costs to watch** | False-decode rate, CPU per slot, latency, allocations, any regression in the other nine benchmarks |
| **Safety surface** | Whether it touches `txgate`, PTT, the transmit path, the audio callback or `unsafe`; if so, which tests in `AGENTS.md` §4 guard it |

Fixing the decision rule in advance is the point of this step. Moving seeds, sample sizes, SNR
points or exit conditions after seeing a result is prohibited (`AGENTS.md` §5).

## 2. Experiment against the `main` baseline

The baseline is the `main` commit the branch forks from, **built and measured under the same
conditions as the candidate**. A figure copied from `docs/benchmarking.md` is context, not a
baseline, unless its `research/results/<commit>/` directory is for that exact commit.

Requirements:

- **Same instrument.** Both sides run `z30 --benchmark …` (`crates/z30-cli/src/suite.rs`), which
  calls `decode_slot` and nothing else. No benchmark-only decoder, no receiver code that knows it
  is being measured (`AGENTS.md` §4, "One receiver, one modulator").
- **Same seeds.** Both sides use the suite seed (20260830) and the same `--frames`. Additional
  statistical power comes from `--replicate 1…n`, never from a different base seed (replicates
  are disjoint by construction; small base seeds reused published frames — corrective audit §D).
- **Paired where it compares.** Candidate and baseline decode the same audio; report the exact
  two-sided McNemar p-value over the discordant frames, as the `sic` benchmark does.
- **Confidence intervals on everything.** Rates carry Wilson 95% intervals; crossings carry the
  interpolated Wilson bounds; a zero count carries the one-sided Clopper–Pearson 95% limit.
  At least 200 frames per point behind a sensitivity crossing; fewer is exploratory and is
  labelled so.
- **False-decode rate.** Run `z30 --benchmark false` on both sides. A candidate that adds decodes
  and adds any false decodes must say so, with the interval, in the first line of its result.
- **CPU cost.** Run `z30 --benchmark perf` on both sides on the same idle machine: p50/p95/p99
  latency, CPU seconds per slot and allocations per slot at K = 1, 5, 20, 50, one and all threads.
  The real-time budget (window closes at slot + 25.5 s, next slot at + 30 s) and the targets in
  [benchmarking.md](benchmarking.md#performance-gate-g27) are the reference.
- **No collateral regressions.** Run the full `z30 --benchmark suite` on both sides. Any of the
  ten benchmarks that moves is reported, not only the one the proposal targets.
- **Clean tree, recorded provenance.** Build from a committed, clean tree; the result JSON records
  commit, dirty flag and diff hash, toolchain, `RUSTFLAGS`, CPU and its ISA features, threads,
  `Cargo.lock` hash, instrument identity, seed rule and `RxConfig`, and a `status`. Results go in
  `research/results/<commit>/` for both commits and are never edited; `SUMMARY.md` is generated by
  `research/summarize_suite.py --write`. `z30` writes there only a clean, published-seed,
  full-size run and never overwrites a published file; a dirty build, an exploratory size or a
  replicate is routed to a labelled directory instead ([benchmarking.md](benchmarking.md)).
- **Frame-level pairing across commits.** Run both sides with `--per-frame` and pair the
  `<name>.frames.jsonl` files with `research/paired_mcnemar.py`; compare whole directories with
  `research/compare_results.py`. Both refuse (exit 2) results that differ in seed, replicate,
  frame count or instrument identity, or a benchmark missing from either side.

Reproduce a result from its commit and seed alone:

```bash
git checkout <commit>
cargo build --release -p z30-cli
./target/release/z30 --benchmark suite                    # or: --benchmark <name> [--frames N] [--replicate R] [--per-frame]
./target/release/z30 --benchmark perf
python research/summarize_suite.py research/results/<commit> --write
python research/compare_results.py research/results/<baseline> research/results/<candidate>
python research/paired_mcnemar.py <baseline>/awgn.frames.jsonl <candidate>/awgn.frames.jsonl --bootstrap 10000 --bootstrap-seed <S>
```

### 2a. Comparing sensitivity crossings between two commits

> **Process change proposed on 2026-09-28 (audit RES-16 / F-40). It is not in force until the
> board accepts it on a pull request**; until then it is the recommended method, and a proposal
> that uses it says so.

A claim in dB ("the 50% AWGN crossing moves by ≥ 0.2 dB") needs a statistic in dB, and the
per-curve Wilson intervals say little about the difference between two strongly correlated,
paired curves. The proposal fixes, before any run:

1. **The frames.** Benchmark, SNR points (e.g. awgn −24…−22 dB), and replicate set (e.g.
   replicates 0–4, 1000 frames per point). Both sides run with `--per-frame`; the pairing unit
   is (benchmark, point, frame, seed), and the instrument identity must match
   (`paired_mcnemar.py` refuses otherwise). **Today `paired_mcnemar.py` pairs one replicate at a
   time** and takes every point in the file as the Holm family; pooling several replicate pairs
   and restricting the family to the pre-registered points are not implemented (ledger F-82).
   Until they are, pre-register one replicate with the frame count you need, run it with `--out`
   (a clean replicate-0 run at or above the publishable size without `--out` takes the commit's
   published slot), and recompute Holm over the pre-registered points from `--json`'s per-point
   `mcnemar_exact_p`. Busy-band records share a slot's audio, so their pairs are clustered and
   McNemar's p-values for `busy` are too small; false decodes are not paired (use `false.json`).
2. **Acceptance statistic.** At each pre-registered point, the exact two-sided McNemar test over
   the discordant frames; across the points, Holm's step-down correction at the proposal's α
   (default 0.05). A point has moved if its Holm-adjusted p < α, in the direction of the larger
   discordant count. The pooled McNemar over the range is reported beside it. Because pairing
   is deterministic, any discordance at all is reported, including outside the claim.
3. **Effect size.** The 50% crossing delta Δ = candidate − baseline, by the suite's linear
   interpolation, with a paired bootstrap percentile 95% interval: B = 10 000 draws, frames
   resampled with replacement within each point, the same draw applied to both sides, the
   bootstrap seed S written in the proposal. If more than 2.5% of draws fail to bracket 50% on
   either side, the interval is "not defined" and the result is inconclusive; the range is
   widened only in a new proposal.
4. **Decision.** A claimed shift of at least δ dB is accepted when Holm finds at least one
   point moved in the claimed direction and none against it, **and** the whole 95% interval of
   Δ lies on the claimed side at a distance of at least δ from zero. A "no worse than m dB"
   claim is accepted when the unfavourable end of the interval is within m. Anything else is
   reported as the rule's outcome, not reinterpreted.

Power, for sizing (from the pooled 2200-frame AWGN curve, slope ≈ 54 percentage points per dB
at 50%): a one-directional 0.2 dB shift gives about 22 discordant frames in 200 per point; a
0.05 dB shift about 5, which needs about 1000 frames per point (five pre-registered replicates).

The deliverable of this step is a **results note** in the pull request: baseline and candidate
commits, the table from each `SUMMARY.md`, the deltas with intervals and p-values, false decodes,
CPU cost, and a one-line verdict against the decision rule written in the proposal. A result that
fails the rule is still reported; negative results are recorded, not discarded.

## 3. Review

A pull request is ready for the board only when all three reviews are recorded on it.

| Review | Owner | Checks |
| :--- | :--- | :--- |
| **Code** | CTO | CI green on Linux/Windows/macOS and MSRV; fmt, clippy `-D warnings`, tests; no safety test weakened; no new `unsafe` or panic path in the audio callback or real-time threads; determinism (identical at any thread count, no unseeded RNG on the receive path); golden vectors unchanged unless the change is a protocol change; docs, wiki and `SPEC.md` agree with the code; smallest diff that proves the point |
| **DSP** | RF engineer | The change does what the proposal says for the reason it says; the channel model and SNR definition (SPEC §10) are appropriate; no genie-aided shortcut is reported as a threshold; the claim holds beyond the benchmark's exact conditions or its limits are stated |
| **QA reproduction** | QA | An independent rebuild of **both** commits reproduces the published counts exactly from commit and seed. Any difference is a finding, not a rounding issue |

Findings are written with severity, `file:line` evidence and a proposed fix. The author answers
each one in the pull request, by a change or by a stated reason.

## 4. Board decision

The CEO brings the pull request, the results note and the three reviews to the board. The board
**explicitly** accepts, rejects or asks for more evidence, and that decision is recorded on the
pull request (or linked from it). Silence, elapsed time or a passing CI run is not acceptance.

Acceptance applies to the reviewed head commit. A push after acceptance, other than a rebase with
no content change, sends the pull request back to section 3 for the changed part.

## 5. Merge

After acceptance, the pull request is merged as reviewed. The same pull request (not a follow-up)
carries:

- the `research/results/<commit>/` directories for baseline and candidate;
- updated [benchmarking.md](benchmarking.md) and `AGENTS.md` §5 figures, pasted from
  `SUMMARY.md`, when a published figure moves; superseded figures are marked withdrawn and kept in
  the history, not silently replaced;
- updated `docs/`, `wiki/` and `SPEC.md` wherever they describe the changed behaviour.

## 6. Protocol changes

A change to anything `SPEC.md` specifies — the waveform, Costas array, symbol map, CRC, LDPC
code, message codec, slot timing or SNR reference — is a **protocol change**: it breaks
interoperability with every existing station. On top of sections 1–5 it requires:

1. **`SPEC.md` updated** in the same pull request, with the new version number in its title and
   a statement of what changed and why. Section 12 already requires that a v2 make the protocol
   version explicit on the air.
2. **New golden vectors.** The v1 vectors in `fixtures/golden/` were generated by the Python
   oracle, which defined v1 and was deleted in the 2026-10-06 cleanup; they cannot be
   regenerated and are pinned byte for byte by `fixtures/golden/FROZEN.sha256`. They are never
   edited by hand or replaced. A new version's vectors come from a reviewed generator committed
   with them under `research/golden/` (outside the application, where CI's hygiene job allows
   Python and a pinned `research/golden/requirements.txt`), are written to their own directory
   beside the v1 set (`fixtures/golden/v2/`, with its own `FROZEN.sha256`, which CI checks), and
   are hash-pinned in the same commit with the reason. The same pull request adds a CI step
   that runs the generator's `--check` mode (regenerate into a temporary directory and compare
   byte for byte), so the new vectors are reproduced, not only pinned. The generator should be
   independent of `crates/` - that independence is what the v1 oracle gave and what a copy of
   the Rust code would not. The v1 vectors remain for as long as v1 is supported.
3. **A version bump**: `z30_protocol::PROTOCOL_VERSION` (`crates/z30-protocol/src/lib.rs`,
   reported by `z30 --version` and the GUI), the workspace version in `Cargo.toml`, and a
   release note stating that the change is not compatible with earlier versions.
4. **Board acceptance as an operator decision**, not only as a merge approval
   ([development.md](development.md#house-rules-for-the-workspace)).

## 7. What does not need an experiment

Changes that cannot move a measured figure — documentation, CI, tooling outside the receive and
transmit paths, dependency updates that leave the benchmark suite bit-identical — skip section 2
but not sections 3–5: they are still code-reviewed and still merge only with board acceptance.
Where the suite is claimed to be unchanged, the pull request shows it with
`research/compare_results.py` (all ten benchmarks IDENTICAL; it refuses to compare results that
differ in seed, frame count, status or instrument). The earlier script at
`audit/2026-09-24-corrective-remediation/evidence/scripts/compare_results.py` is kept as that
audit's evidence; it did not check any of these.

For a **dependency update** there is a cheaper proof that is still a proof, and it is the one to
reach for first:

```bash
git show <base>:Cargo.lock > /tmp/base.lock
git show <head>:Cargo.lock > /tmp/head.lock
python3 research/lock_closure.py /tmp/base.lock /tmp/head.lock     # exit 0 = unchanged
```

`lock_closure.py` compares the resolved dependency closure of `z30-cli` (the binary that runs the
suite) and `z30-dsp` (the receiver) between the two lock files. If no crate in either closure
changes name, version or source, the suite is built from an identical set of inputs and no
measured figure can move — that is sufficient, and the update is a section 7 change. It needs no
toolchain and no hour of compute, so a reviewer can always produce it.

It proves one direction only. When a closure **does** change, section 7 does not apply on this
evidence: the update reaches the measurement and needs the suite on both commits. For a crate
outside the benchmark instrument - one not in the `channel_dependencies` a result records
(`build_support.rs` hashes the whole resolved closure of `z30-channel` and `z30-protocol`, dev
dependencies included, so `serde` and `serde_json` are in it) - that means `compare_results.py`
on the two result directories, which must say IDENTICAL; for example a `toml` bump in `z30-io`
that moves no version in that list. Anything in that list is part of the instrument identity,
and `compare_results.py` and `paired_mcnemar.py` refuse to compare across it. A bump to `rand`,
`rand_chacha` or `rand_distr` is the plainest case: they generate every seeded channel
realisation (`crates/z30-channel/src/lib.rs`). Such a bump is an
instrument change: its own proposal, `suite`, `false` and `perf` on both commits, and a
deliberate re-baseline under section 5 (the old results superseded and kept), never absorbed
quietly into a routine bump.

Section 3 still applies either way. A section 7 change whose CI is red does not land, however
sound its bit-identical proof is.
